# Native HQP status

Обновлено: 2026-08-02

## Краткий вывод

`HierarchicalQpSolver` — рабочая нативная dense-реализация строгой
лексикографической иерархии линейно-квадратичных задач. Это уже не макет: API
экспортируется из `termin_qopt`, solver проходит общий JSON oracle и отдельные
C++ тесты. Однако сейчас HQP является изолированным solver foundation, а не
готовым контуром управления роботом: `DynamicsSystem` и текущий 3D маятник его
не вызывают.

## Что реализовано

- Уровни с уникальным целочисленным priority; меньшее число означает более
  высокий приоритет. Порядок регистрации на порядок решения не влияет.
- Квадратичные задачи `||Jx - target||²_W` с симметричным положительно
  полуопределённым весом `W`.
- Жёсткие равенства `Ax = b` и неравенства `Cx <= d`. Ограничение начинает
  действовать на объявившем его уровне и остаётся действующим ниже.
- Каждый уровень решается нативным active-set QP в текущем допустимом
  подпространстве. После решения допустимые направления пересекаются с
  nullspace равенств и положительно-взвешенной части task Jacobian, поэтому
  младшие задачи сохраняют достигнутое значение старших задач.
- Входные task/constraint buffers копируются при регистрации. Выходные buffers
  записываются только после полного `Optimal`; несовместимый младший уровень
  возвращает semantic status и `LevelSolveFailure`.
- Публичный ABI не содержит Eigen. Eigen используется только внутри backend.

## Что проверяют тесты

Общий solver oracle покрывает один уровень, использование nullspace младшим
приоритетом, ограниченный младший уровень, сохранение full-rank задачи,
равенство и redundant robotics Jacobian. Дополнительный C++ corpus проверяет
несовместимый младший уровень, duplicate priority и корректную семантику
полуопределённого веса. Nullspace отдельно проверяется QR- и SVD-политиками.

Целевой тест: `termin_qopt_hqp_test`.

## Ограничения и технические хвосты

- API всё ещё provisional: Python bindings и совместимость со старым Python
  `HQPSolver` намеренно не сделаны.
- Это dense solver для малых задач. Sparse backend, переиспользование
  факторизаций и сохраняемый warm start между вызовами отсутствуют.
- `initial_primal` задаёт исходную точку/смещение решения, но не передаёт
  active-set warm start во внутренние уровни.
- HQP API принимает общие неравенства, но пока не выставляет отдельные
  lower/upper bounds, хотя нижележащий active-set QP их умеет.
- Жёсткие ограничения не имеют slack/relaxation policy. Несовместимое
  ограничение младшего уровня делает весь solve неуспешным; это строгая
  семантика, а не weighted-priority controller.
- `level_task_residual_l2` публикует обычную, невзвешенную норму residual.
  Для вырожденного `W` она может включать строки, которые задача сознательно
  не оптимизирует; это диагностическое значение, не стоимость уровня.
- `failed_level` является индексом в отсортированном по priority порядке, а не
  самим priority и не индексом регистрации.
- Пересечение двух output views явно не отвергается. До объявления стабильного
  API требуется либо запретить aliasing проверкой, либо определить его
  семантику.
- Текущий corpus невелик: нет controller/runtime integration, масштабных
  ill-conditioned задач и систематических комбинаций active inequalities на
  нескольких уровнях.

Итого: solver пригоден для следующего интеграционного прототипа и расширения
тестов, но считать его production-ready HQP-контроллером пока рано.
